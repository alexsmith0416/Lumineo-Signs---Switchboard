# BCPush_PoReceipts + BCPush_PoDeliveries — warehouse receiving into Business Central

> **Built Oct 8, 2026 — not yet published / imported.** Warehouse Management
> phase 3. Receiving happens in the Switchboard app (Warehouse Management, the
> Jobs list POs column, the job panel); these two flows mirror it into BC so
> people working in BC see it on the **Purchase Order card** and the **Job
> Card**. Dataverse stays the source of truth; BC only displays it.
> Nothing here posts a BC receipt or touches BC's purchase documents — whoever
> wrote the PO still posts the receipt.

## What BC shows (ext `bc/lumineo-planning-ext` v1.0.0.18)

| Where | What |
|---|---|
| **Purchase Order card** (page 50) | *Vendor Status (Switchboard)* next to Status (FlowField on Purchase Header, tableext 58420); a **Receiving (Switchboard)** part under the lines — each delivery: date, storage location, last delivery ✓, received by, notes (page 58424). |
| **Job Card** (page 88) | a **PO Receiving (Switchboard)** part under the tasks — each of the job's POs: Vendor Status (green Received / amber Partially Received / red Delayed, On Hold), deliveries (click for the list), last received, **Stored At** (every location, newest first) (page 58425). Click a PO No. to open the PO. |

All read-only in BC. Objects:

| Object | |
|---|---|
| table 58420 `LUM PO Receipt` | one row per PO: PO No. (key), Project No., Vendor Status, Status By / At; FlowFields Deliveries, Last Received |
| table 58421 `LUM PO Delivery` | one row per delivery: Id (the app's delivery id = Dataverse row id), PO No., Project No., Date Received, Received At (site, v1.0.0.18), Storage Location, Received By, Notes, Last Delivery |
| page 58422 `poReceipts` (API) | keyed by `poNo`: `poReceipts('PO-1234')` |
| page 58423 `poDeliveries` (API) | keyed by `id`: `poDeliveries(<guid>)` (unquoted) |
| pageext 58420 / 58421 | Purchase Order / Job Card |

Both tables have `InherentPermissions = RIMD` (like `LUM Task Completion`), so
the flows' app user writes them and every BC user reads them — **no permission
set to assign**.

## The flows (solution `BCPoReceiving`)

Generated by `_gen_poreceiving_flows.py`, zipped by
`_build_poreceiving_solution.py` → `Downloads\BCPoReceiving_1_0_0_2.zip`.

| Flow | Trigger | Does |
|---|---|---|
| **BCPush_PoReceipts** | `crfdf_poreceipt` added / modified | re-reads the row; `GET poReceipts?$filter=poNo eq '…'` → `PATCH poReceipts('…')` (If-Match *) or `POST poReceipts` |
| **BCPush_PoDeliveries** | `crfdf_podelivery` added / modified / **deleted** | added / modified: re-reads the row, then `PATCH poDeliveries(<id>)` or `POST` (with `id`). Deleted: if it reached BC, `DELETE poDeliveries(<id>)` |

- **One run at a time** per flow, so quick edits of one row land in order.
- **Re-read first**: a run writes the row as it is NOW, never the trigger's
  snapshot — a late run can't put an older value back. A row deleted before
  its add/modify run gets there is skipped.
- Text is cut to BC's field lengths (Vendor Status 30, location / received by
  100, notes 250); PO / job numbers go upper-case (Code[20]).
- Auth: the same app registration as the other BC flows (`Bc_ClientId`,
  `Bc_ClientSecret` — set at build time from `$env:BC_CLIENT_SECRET`, never
  committed). UAT parameters by default; Production cutover = `Bc_ApiBase` /
  `Bc_CompanyId` like `BCSync_JobPOs`.

## Go-live (in order)

0. **Dataverse columns** (Oct 9): `scripts/add-receiving-site-columns.ps1`
   (`crfdf_podelivery.crfdf_site`, `crfdf_appuser.crfdf_homesite`). The
   deliveries flow selects `crfdf_site`, so it must exist first.

1. **Publish BC ext v1.0.0.18** to UAT (VS Code → AL: Publish, launch config
   "UAT sandbox"; or upload `Lumineo Signs_lumineo-planning-ext_1.0.0.17.app` in
   Extension Management). Check a Purchase Order and a Job Card show the new
   (empty) parts.
2. **Build + import the flows**: `$env:BC_CLIENT_SECRET="<secret>"; python
   _build_poreceiving_solution.py`, import `BCPoReceiving_1_0_0_2.zip`, map the
   Dataverse connection reference. Built without the secret? Run
   `scripts/copy-bc-secret-to-flows.ps1` — it copies it from an existing BC
   flow (the designer has no field for definition parameters). Then turn
   **both** flows on.
3. **Test**: receive a delivery on a real PO in the app → the PO's Receiving
   part and its job's PO Receiving part show it within a minute; remove the
   delivery (×, Admin / Ops) → it disappears from BC.
4. **Backfill** what was received before step 2:
   `scripts/backfill-bc-poreceiving.ps1` (dry run), then `-Apply`.

## Not in this phase

- Stock POs (no job), expected receipt dates ("expected this week / overdue"
  lists) — phase 4 widens the PO query + `BCSync_JobPOs` for them.
- Editing receiving in BC. BC is a mirror; to change it, change it in the app.
