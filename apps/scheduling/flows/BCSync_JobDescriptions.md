# BCSync_JobDescriptions — job descriptions in the job panel

**What it does.** Every hour it copies each open job's three BC descriptions
into `crfdf_jobdesc`, so the job panel can show them as click-to-open sections:

| Section | BC field | Who sees it |
|---|---|---|
| Field Description | `ICG.LMN.FieldDescription` (60215) — install instructions, prints on the traveler | everyone |
| Production Description | `ICG.LMN.ProdDescription` (60214) — production instructions, prints on the traveler | everyone |
| Extended Description | `ICG.LMN.ExtendedDescription` (60202) — the sales / proposal text | editors only |

Source: generated by `_gen_jobdesc_flow.py` → `BCSync_JobDescriptions-clientdata.json`;
packaged by `_build_jobdesc_solution.py` → `Downloads\BCJobDescriptions_1_0_0_1.zip`
(solution **BCJobDescriptions**). Edit the generator, never the JSON. Table:
`scripts/create-jobdesc-table.ps1`. App: `services/job-descriptions.ts`,
`hooks/useJobDescriptions.ts`, `Description` in `components/JobInfoSections.tsx`.

## Order Type (v1.0.0.2 of the flow, BC ext v1.0.0.15) — the Service stepper

The same page and flow also carry each job's **Order Type** (Job Card "Order
Type": SERVICE, SIGNCONT, MNTCCONT, SALES, GRAPHICS…) into
`crfdf_jobdesc.crfdf_ordertype` — SERVICE / SIGNCONT / MNTCCONT jobs get the
app's Service stepper (`src/services/service-steps.ts`).

- The field isn't in any BC API and its number isn't in the Infotech symbols
  we have (Sign365, Lumineo Signs - Projects, Shop Floor). Page 58403 looks
  for a Job field **captioned "Order Type"**, else reads Sign365's 95294
  "Service Order" (`orderTypeField` says which). In UAT neither works — the
  caption is the Card PAGE's, and 95294 is blank everywhere — so **v1.0.0.16**
  derives the code from **Description 2**, which BC fills with the order
  type's NAME: the Resource with that Name ("Service Order" → SERVICE). UAT,
  Oct 7: 698 of 707 open jobs resolve — 225 SALES, 185 OUTSOURCE, 136
  SERVICE, 65 GRAPHICS, 58 OUTDOORADV, 17 NATIONAL SALE, 8 MNTCCONT, 3
  LUMINOUS, 1 SIGNCONT; 9 blank (Description 2 typed over by hand). Test job:
  **J38696** (SERVICE).
- The order type is part of the flow's change stamp, so the first run after
  this version writes every job that has one (their lastModified didn't move).
- **Order matters:** publish BC ext v1.0.0.15 → run
  `scripts/add-jobdesc-ordertype-column.ps1` → import
  `BCJobDescriptions_1_0_0_2.zip` (over 1.0.0.1) → Run. With the old page the
  flow fails on `$select=orderType`; without the column the writes fail.

## Where the text comes from (BC)

The three fields are **Blobs** that Infotech's **"Lumineo Signs - Projects"**
extension (c4333fb6, tableextension 60200 `ICG.LMN.Job`) adds to Job — which is
why no BC API or query returned them. Our API page **58403 "Lumineo Job
Descriptions API"** (`bc/lumineo-planning-ext` v1.0.0.11+) reads them into text:
`api/lumineo/planning/v1.0/companies(<id>)/jobDescriptions` — `jobNo`, `status`,
`lastModified` (the Job's SystemModifiedAt), `fieldDescription`,
`productionDescription`, `extendedDescription`.

- Reads by field **number** through RecordRef, so there's no dependency on
  Infotech's extension; a missing field reads as "".
- Encoding: BC writes Blobs in its default **MSDos** encoding unless told
  otherwise, and that's how these are stored (’ = byte C2, ” = C4). Reading
  them as UTF-8 threw *"Invalid data encountered in stream"* for the whole
  response (v1.0.0.9); a Windows fallback (v1.0.0.10) showed ’ ” as Â Ä
  (J29295 "5Â-10Ä"). v1.0.0.11 tries UTF-8, then MSDos — matches BC's screen.
- Plain text, no HTML. UAT Oct 5 2026: 707 open jobs (read in ~6 s); 610 have a
  Field, 319 a Production, 703 an Extended Description; longest 3,516 chars.
- Symbols of the Infotech extensions were downloaded with
  `/dev/packages` (device-code sign-in) to find the fields; not committed.

## How it works (hourly, or Run)

1. **Get_Descriptions** — HTTP GET, open jobs only, app-registration auth.
   **Check_Single_Page** fails the run if BC ever pages the answer.
2. **Changed_Jobs** — jobs whose `jobNo~lastModified` isn't already in the
   table (`crfdf_jobno~crfdf_bcmodified`). Saving a description in BC moves the
   Job's SystemModifiedAt, so only edited jobs are written (10 at a time:
   update the job's row, or create it).
3. **Stale_Rows** — rows for jobs that are no longer open are deleted. Skipped
   if BC returned no jobs.

The first run writes every open job (~700 rows); after that an hour costs a
handful of writes.

## Import & test

1. Run `scripts/create-jobdesc-table.ps1` (creates `crfdf_jobdesc`).
2. Power Apps → Solutions → Import `BCJobDescriptions_1_0_0_1.zip`; bind
   **Microsoft Dataverse** to the existing connection. It imports **Off**.
3. Turn it on → **Run**. First run ~700 rows, a few minutes.
4. In the app open a job card → ▸ Field Description / ▸ Production Description
   (and ▸ Extended Description as an editor). J29295 (UAT) has all three.
