# BCSync_NewOrders — new jobs onto the Jobs list the moment they're released

**What it does.** When the expeditor checks **Started** on a job's **New Order
This Week** step in BC Project Planning, the job appears on the app's Jobs list
within about 15 minutes — or about a minute after someone presses **Check BC
now** on the Jobs list — with Current Status **New Order this week** and
everything BC knows already filled in. Without it, a new job only shows up the
next morning, as "Not tracked yet".

Source: generated by `_gen_neworders_flow.py` → `BCSync_NewOrders-clientdata.json`.
Edit the generator, never the JSON. Since Oct 12, 2026 it ships in the
**BCCheckNow** solution (`_build_syncnow_solution.py`) with the other BC pulls;
`_build_neworders_solution.py` (BCNewOrders 1.0.0.2) is the older single-flow
package.

## When it runs (Oct 12, 2026)

On a **Check BC now** request — a `crfdf_syncrequest` row of kind `neworders`,
added by **BCSync_Scheduler** every 15 minutes or by the app's **Check BC now**
button, which then reloads the Jobs list and shows the result ("Added 2 jobs:
24-1234, 24-1240" / "No new orders to add"). One run at a time, so a job is
never added twice. See **CHECK-BC-NOW.md**.

## What each run does

1. **Get_Started_Steps** — HTTP GET on our web service `LumineoProjectPlanning`
   (page 58400, `bc/lumineo-planning-ext`), app-registration auth (same as
   `BCPush_PlanningSteps`): rows with `Started eq true` changed in the last
   `Lookback_Days` (3). `Step_Description` is computed on the page (step GUIDs
   differ per environment), so BC can't filter on it; **New_Order_Steps** keeps
   the rows whose step is `New_Order_Step` (case-insensitive). The 3-day window
   keeps years-old New Order rows out and covers a weekend or a flow outage.
2. Nothing new → the run ends (a handful of actions).
3. **Untracked_Jobs** — those job numbers minus the ones that already have a
   `crfdf_jobtrack` row. A job that's already on the list is never touched, so
   its status isn't overwritten.
4. **For_each_new_job** (one at a time):
   - **Get_BC_Job** (BC connector, analytics `jobs`) — skipped unless the job is
     **Open** and not complete.
   - **Add_To_Jobs_List** — creates the `crfdf_jobtrack` row:
     `crfdf_statusoverride` = `New_Order_Status` ("New Order this week").
   - **Fill_In_From_BC** (best-effort scope; a failed read still leaves the job
     on the list and the nightly flows fill it in):
     - sign365 `jobs` → release date (Order Date, DIP, Mfg / Install Target)
     - bill-to customer (`crfdf_bccustomers`) → customer name, fallback address
     - first Order `salesLines` row → document no, remaining balance, salesperson
     - that `salesOrders` row → ship-to name (the job name), ship-to address /
       city / state / zip (Location), order amount (Value), salesperson
       (Sales, Region)
     - creates or updates the `crfdf_bcjobs` row with all of it (the same
       columns BCSync_Jobs / BCSync_SalesLines / BCSync_JobReleaseDates write)
     - analytics `jobPlanningLines` (Resource + Billable) → `crfdf_bcplanninglines`
       (create or update), so the stepper, Crating and the lead-time targets
       appear straight away.

## Parameters

| Parameter | UAT (now) | Production (at cutover) |
|---|---|---|
| `Bc_ODataBase` | `…/fe0182fa-…/UAT/ODataV4` | `…/fe0182fa-…/Production/ODataV4` |
| `Bc_Environment` (connector) | `UAT` | `PRODUCTION` |
| `Bc_CompanyId` | `4738bfb5-a06d-ec11-bf27-000d3a132a9e` | confirm |
| `Bc_Company` / `Bc_Service` | `Luminous Neon` / `LumineoProjectPlanning` | same |
| `Bc_ClientId` / `Bc_ClientSecret` | the Postman app registration | the prod app registration |
| `New_Order_Step` / `New_Order_Status` | `New Order This Week` / `New Order this week` | same |
| `Lookback_Days` | `3` | same |

Switching to Production needs the **production cutover** first (START-HERE →
PRODUCTION CUTOVER): the extension (page 58400) in Production and the app
registration's permissions there. Then change the two environment parameters
(and the client id / secret if prod uses another registration) and save.

## Import & test (UAT)

1. Build: from `flows/`, run the build with the secret (see
   `_build_neworders_solution.py`; `$TEMP/build-neworders.ps1` reads it from
   the Postman env file). The zip goes to Downloads, outside the repo.
2. Import the **BCCheckNow** solution and copy the secret back — see
   CHECK-BC-NOW.md → Build & import.
3. Make sure BCSync_NewOrders and BCSync_Scheduler are **On**.
4. Test: in **UAT** BC, pick an open job that's on the Jobs list as *Not tracked
   yet* (or not on it at all), and check **Started** on its **New Order This
   Week** step. Press **Check BC now** on the Jobs list: within about a minute it
   shows as *New Order this week* with its name, Sales / Region / Location, Order
   Date, Value and stepper (or wait for the 15-minute check and press **Refresh**).

⚠️ UAT test runs write to the same Dataverse the live app uses — a UAT-only job
you test with will appear on the real Jobs list. Test with a job that exists in
Production too, and set its status back afterwards (or ask Claude to remove the
test rows).
